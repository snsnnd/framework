# EFW 框架设计与 Review 指南

本文是当前 EFW Runtime 的阅读入口。它解释框架已经实现的设计，而不是假设
EFW 是一个自带线程、内存管理和驱动发现能力的操作系统。阅读源码时建议先看
本文，再沿着公共头文件进入对应的 `.c` 文件。

## 1. 框架定位

EFW 是面向裸机和轻量 RTOS 的 C 运行时框架，核心目标是：

- 不使用 `malloc`，所有注册表和队列容量在编译期或初始化时确定。
- 用统一的 `efw_status_t` 返回错误。
- 用 `ops + ctx` 回调结构隔离芯片、协议、设备和业务实现。
- 用名称把不同层连接起来，使上层不直接依赖 BSP 句柄。
- 允许通过编译宏裁剪功能，避免未使用模块进入最终固件。

EFW 不负责：

- 中断向量、线程调度、锁、堆分配和硬件时钟的默认实现。
- 自动发现硬件或自动推断 `void *` 指针指向的数据类型。
- 替应用决定控制周期、数据单位、协议帧格式和故障安全策略。

## 2. 分层和依赖

```text
应用 / Graph 生成代码
        |
        +-- Module：生命周期和业务轮询
        +-- State Machine：状态转换和业务状态
        +-- Algorithm：PID、滤波、估算等纯计算入口
        +-- Device：Sensor 读 / Actuator 写
        +-- COMM：协议、帧、收发、超时
        +-- HAL：GPIO、ADC、UART、I2C、SPI、PWM 等硬件操作
        |
        +-- Core：状态码、注册表、事件队列、调度器、诊断
        +-- Debug / LiteTune：可选观测与在线调试
```

注册时的典型依赖方向是：

```text
HAL -> COMM -> SENSOR / ACTUATOR -> ALGORITHM -> MODULE / STATE MACHINE
```

这里的箭头表示“后者可能通过名称引用前者”。`efw_init()` 只初始化空注册表，
不替应用注册对象。应用必须在 `efw_init()` 后按依赖顺序注册和绑定。

## 3. 统一对象模型

大多数框架对象都遵循同一模式：

```c
typedef struct {
    const char *name;             /* 框架索引键 */
    void *ctx;                    /* 用户拥有的私有状态 */
    efw_status_t (*operation)(void *ctx, ...); /* 框架调用的入口 */
} some_ops_t;
```

注册表只保存 `ops` 指针，不复制 `ops`、`name` 或 `ctx`，也不负责释放它们。
因此有三个必须遵守的生命周期规则：

1. `ops` 和其中的名称字符串必须是静态对象或在注销前一直有效的对象。
2. `ctx` 必须在任何回调可能被调用期间保持有效。
3. 注销只删除索引，不会自动执行 `stop`、`disable`、`close` 或释放资源。

默认查找是 `strcmp` 线性扫描。注册表规模较小时这换来了简单、可读和确定的
实现；高频控制路径不要每周期按名称查找，应在初始化阶段调用 `get` 缓存
`ops` 指针。循迹跟随器就是这种缓存句柄的示例。

## 4. 启动和运行时序

### 4.1 最短启动路径

```text
efw_init()
  -> 清空诊断
  -> 初始化 HAL / COMM / MODULE / SENSOR / ACTUATOR / ALGORITHM
  -> 初始化状态机 / 事件队列 / 调度器

应用注册阶段
  -> 注册 HAL
  -> 注册 COMM（校验 hal_name）
  -> 注册 Sensor / Actuator（校验 hal_name、comm_name）
  -> 注册 Algorithm、State Machine、Module
  -> 初始化设备和状态机

运行阶段
  -> efw_scheduler_tick() 或应用自己的周期循环
  -> efw_module_poll_all() / 直接调用缓存句柄
  -> efw_event_queue_process()
  -> 可选 Debug / LiteTune 更新和传输
```

### 4.2 Manifest 启动路径

`efw_app_init()` 在 `efw_init()` 后按以下固定顺序调用非空步骤：

```text
init_pools -> register_platform -> register_components -> bind_handles
```

任一步返回错误，后续步骤不执行。当前实现会把应用阶段通过 trace 回调暴露
出来，但不会自动回滚已经完成的注册；失败后的清理由应用决定。

`efw_app_update_1ms()` 只是调用 manifest 的 `update_1ms`，名称中的 1ms 是
应用契约，不代表框架会创建 1ms 定时器或保证调用频率。

## 5. 各层设计

### 5.1 HAL

HAL 是最底层的硬件操作接口。它不解释协议，只提供 `init/read/write/ioctl`。
具体芯片 SDK 的句柄、寄存器地址和 DMA 状态放在 `ctx` 中，由 BSP 回调解释。

review HAL 时必须确认：

- `read/write` 的阻塞、超时和 `actual` 语义是否明确。
- 回调是否可能在 ISR 中调用，是否会访问非 ISR 安全 API。
- `ctx`、DMA 缓冲区和外设句柄的生命周期是否长于注册表。
- 错误是否被正确转换为 `EFW_ERR_IO` 或更具体的状态码。

### 5.2 COMM

COMM 位于 HAL 之上，负责协议帧、地址、校验、超时和重传。注册时通过
`hal_name` 进行早期依赖校验。`open/close` 可以为空，`send/recv` 是必填入口。

当前注册校验证明“名称引用存在”，但不证明 HAL 类型和 COMM 类型匹配；例如
把 UART 协议绑定到一个语义上不合适的 HAL，仍需要应用或更强的契约校验发现。

### 5.3 Sensor 和 Actuator

Sensor 和 Actuator 是对称的设备层：

```text
Sensor：init -> read
Actuator：init -> enable -> write，必要时 disable
```

两者都可以绑定 HAL、COMM、两者都不绑定，或同时绑定两者。绑定字段是名称，
设备回调通过 `ctx` 解释具体数据格式。

Actuator 的 `enable/disable` 与 `write` 分离是安全设计：输出值为零不一定代表
驱动器断电或执行器进入安全态。急停路径应明确调用 `disable`，不能只写零。

### 5.4 Algorithm

算法注册表只知道：名称、分类、`ctx` 和统一的 `run(ctx, in, in_size, out,
out_size)`。`in/out` 的实际类型属于具体算法契约，例如 PID 使用
`efw_pid_input_t` 和 `efw_pid_output_t`。

这带来灵活性，也把类型安全责任交给调用方。review 时要检查：

- 每个 `run` 是否检查输入和输出大小。
- 单位、坐标方向和 `dt` 是否在调用链中保持一致。
- 算法状态是否允许多个实例共享，是否误用了同一个 `ctx`。
- 浮点异常、计数回绕、输出饱和和首次调用初始化是否有测试。

内置 PID、滑动均值、低通、斜坡、编码器速度和互补滤波都采用调用方提供的
状态结构，不需要动态内存。

### 5.5 Module

Module 是软件组件生命周期层：`init -> start -> poll -> stop`。注册时会按
`priority` 插入，数值越小越早执行。空回调被视为成功跳过。

批量 `init_all/start_all/poll_all` 当前策略是：继续遍历全部模块，但只返回第一
个错误，并把错误写入诊断。这个策略要在产品需求中明确，因为它既不是“首错即停”，
也不是“失败模块自动回滚”。

### 5.6 State Machine

状态机上下文由应用拥有，框架保存当前状态、进入时间、转移表和已流逝时间。
`efw_sm_init()` 会立即调用初始状态的 `on_enter`，但不会自动加入全局注册表。
应用必须通过 `efw_sm_set_elapsed()` 提供时间基准。

每次 `efw_sm_tick()` 的逻辑是：

```text
当前状态 on_tick
  -> 如果 on_tick 已自行切换状态，结束本次 tick
  -> 按规则检查 from、timeout、condition
  -> 选择最高 priority 的满足规则
  -> 执行 action
  -> old on_exit -> current=target -> new on_enter
```

状态定义、转移数组和回调都由应用保持有效。转移失败时要确认旧状态的恢复
行为是否满足业务安全要求。

### 5.7 Event

事件模块有两条语义不同的路径：

- `efw_topic_publish()`：同步执行回调，数据指针只在当前调用期间有效。
- `efw_event_queue_post*()` + `process*()`：复制固定大小消息，稍后分发。

队列处理开始时会记录待处理数量，因此处理回调中新入队的消息延迟到下一轮。
队列不是自动并发安全队列；如果生产者来自 ISR、消费者来自主循环，必须在平台
层补充临界区或使用明确的单生产者/单消费者约束。

### 5.8 Scheduler

调度器是非抢占式的 cooperative scheduler。它只在应用调用 `tick()` 时检查
到期任务，不会抢占当前代码。任务槽位保存下一次释放时间、运行次数、错过的
释放次数、启动迟到和运行时间统计。

无时间提供者时，`tick(elapsed_ms)` 的参数被视为当前绝对毫秒时间；设置了时间
提供者后，实际时间来自回调。任务每次 tick 最多运行一次，落后的多个周期进入
`missed_releases`，不会在一个 tick 中连续补跑。

## 6. 调试和 LiteTune

Debug 核心维护固定大小的监控点表，监控点保存名称、来源、类型、值地址和参数
ID。传感器输出类型并不在 `efw_sensor_ops_t` 中描述，因此核心不会猜测
`ops->ctx` 是什么数据；应用必须显式调用 `efw_debug_register_sensor_value()`。

可选后端的职责不同：

- `efw_debug_fast`：变化检测、脏位图和双缓冲，适合快速采集。
- `efw_debug_async`：SPSC 环形缓冲区和 DMA/中断传输，适合不阻塞主循环。
- `efw_debug_runtime`：任务、模块、话题、数据流的运行时统计。
- `efw_debug_litetune`：把监控点和 trace 事件映射到 LiteTune 协议。

使用异步后端时要重点 review 所有权和时序：DMA 未完成前，发送缓冲区不能被
重用；成功发送后必须按配置的同步/异步模式完成回调；ISR 与主循环共享的游标、
统计值和状态必须有平台相关的临界区及内存屏障。

## 7. 推荐的源码 Review 顺序

### 第一步：确认构建边界

检查 `CMakeLists.txt`、`include/efw/core/config.h` 和 `src/efw_all.c`：

- 每个 `EFW_ENABLE_*` 是否同时控制头文件、源文件和实现。
- 功能依赖是否会产生“头文件可见但实现缺失”的配置。
- 聚合编译入口是否因 `.c` include 造成静态符号冲突。
- 最小配置是否能独立编译，不依赖默认全功能配置。

### 第二步：验证生命周期和所有权

沿着 `efw_init -> 注册 -> bind/get -> 运行 -> unregister` 追踪每个对象，逐项问：

- 谁创建对象？谁拥有内存？谁负责销毁？
- 注册表保存的是拷贝还是借用指针？
- 注销、重复初始化和初始化失败之后，状态是否一致？
- 回调执行期间是否允许注册表被修改？

### 第三步：验证错误传播

为每个公共 API 建立状态码表，至少覆盖：NULL 参数、名称不存在、名称重复、
容量耗尽、依赖缺失、设备未就绪、底层 IO 失败和输出缓冲区太小。确认错误是否
同时写入诊断，以及批量操作遇到错误时是停止、继续还是回滚。

### 第四步：验证实时性和并发

- 查找所有可能阻塞的 HAL/COMM/传感器回调。
- 检查主循环、ISR、DMA 完成回调是否共享可变状态。
- 计算最坏执行时间，而不是只看平均时间。
- 检查队列满、DMA 忙、任务错过释放和计数器回绕时的行为。
- 确认浮点、`strcmp`、`snprintf` 和协议序列化是否出现在硬实时路径。

### 第五步：验证数据契约和物理语义

重点核对 `void *` 配对结构体、`*_size`、字节序、单位、符号方向和初始值。
例如：PID 的误差方向、差速电机左右轮符号、IMU 角度坐标系、编码器脉冲倍频、
超声波距离单位和执行器的安全零值都不能只靠函数名推断。

### 第六步：验证故障安全

- 传感器读失败时执行器是否保持安全输出。
- 模块 `poll` 失败是否会停止后续模块或触发降级。
- 状态切换失败后当前状态和硬件输出是否一致。
- 急停是否调用 `disable`，而不是只写一个数值零。
- 通信超时、队列溢出和调试传输失败是否会影响控制回路。

### 第七步：验证测试和可观测性

至少要求：

- 每个注册表的注册、查找、重复、满容量、注销测试。
- 事件队列 FIFO、满队列、零长度数据和回调中新入队测试。
- 调度器首次释放、暂停恢复、迟到、运行超时、时间回绕测试。
- 状态机 enter/tick/exit、优先级、超时、条件和回调失败测试。
- 算法边界测试：`dt=0`、限幅、首次调用、NaN/Inf（若产品允许）。
- 最小编译配置、全功能编译、Debug/Release、32 位和 64 位主机验证。

## 8. 当前代码中应优先确认的风险点

下面不是未经验证的缺陷结论，而是 review 时应优先用测试或平台契约确认的点：

1. 注册表注销通常用末尾元素填洞，注销后遍历顺序可能改变；任何依赖注册顺序
   的应用逻辑都应显式使用 Module priority 或排序，而不是依赖偶然顺序。
2. 各层的名称和 `ops/ctx` 都是借用指针；栈上临时定义的 ops、名称或上下文会
   造成悬空指针，代码 review 要检查存储期。
3. Sensor/Actuator 注册时校验名称存在，但注销底层 HAL/COMM 后不会自动阻止或
   修复上层对象；产品若支持运行时注销，需要增加依赖关系策略。
4. Event、Scheduler、State Machine 和 Debug 的全局状态默认不是通用线程安全
   容器；需要根据实际 ISR/RTOS 调用拓扑确认临界区和重入规则。
5. `void *` 算法接口的大小和数据类型由调用方保证；错误的结构体配对通常无法
   在编译期发现，必须依赖包装 API、代码生成校验和测试。
6. 模块批量初始化/启动/轮询遇错会继续遍历但返回首个错误；要确认继续运行其余
   模块是否符合系统安全要求。
7. 事件消息大小、名称长度、调度任务数量和各注册表容量都是固定上限；需要以
   最坏场景验证容量，而不是只按正常场景配置。

## 9. 一次实际 Review 的输出格式

建议每次 review 最终形成一张表：

| 严重性 | 文件/函数 | 事实 | 影响 | 复现或验证 | 建议 |
| --- | --- | --- | --- | --- | --- |
| Critical/High/Medium/Low | 精确位置 | 当前代码做什么 | 可能破坏什么不变量 | 测试、断言或平台实验 | 最小修复方向 |

优先报告可复现的行为问题和安全问题，再报告可维护性问题。对“设计选择”不要
只说代码看起来奇怪，要指出它依赖的前置条件、违反的契约或缺少的测试。
